# Localization (guest surfaces)

Adopted 2026-09-23 with the French catalog. This is the authority for how a guest ends up
reading the gallery in their language, and for what adding a language involves.

## Scope

Localized: everything a **guest or the couple** sees — the marketing page (`/`), the gallery
(`/g/[token]`), the wedding hub (`/s/[token]`), the password gate, the guest uploader, the
offline panel, the device-transfer dialog, error and not-found pages, the web-app manifest, and
the printable QR sign's guest-facing copy (`src/components/printable-sign.tsx`).

Not localized on purpose: the admin (`/admin`), the photographer's digest e-mail and push
notifications (`src/lib/digest.ts`, `src/lib/push.ts`), and `src/lib/czech-plural.ts` (admin
only). The photographer is one person and reads Czech.

## Languages

| Code | Catalog            | `Intl` tag | `og:locale` | Plural categories used   |
| ---- | ------------------ | ---------- | ----------- | ------------------------ |
| `cs` | `messages/cs.json` | `cs-CZ`    | `cs_CZ`     | `one`, `few`, `other`    |
| `en` | `messages/en.json` | `en-US`    | `en_US`     | `one`, `other`           |
| `fr` | `messages/fr.json` | `fr-FR`    | `fr_FR`     | `one` (0 and 1), `other` |

The vocabulary lives in `src/i18n/locales.ts` (`LOCALES`, `LOCALE_TAGS`, `OG_LOCALES`) and
everything else reads it — negotiation, `<html lang>`, the switcher, date formatting. Czech is
the default (`DEFAULT_LOCALE`): it is the photographer's market, and an undetectable browser is
far more likely Czech than anything else.

## How a guest's language is chosen

Resolution happens per request in `src/i18n/request.ts`, in this order:

1. **The `NEXT_LOCALE` cookie**, if it holds a supported code. Set either by the switcher (a
   Server Action, `src/lib/locale-actions.ts`) or by the first-visit bootstrap below.
2. **`Accept-Language`**, matched with `@formatjs/intl-localematcher` against `LOCALES`. The
   match is by language, so `fr-CA`, `fr-BE` and `fr-CH` all land on `fr`; the order of
   preference is honoured, so `de-DE, fr;q=0.8, en;q=0.7` gets French, not the default.
   Malformed headers and the `*` wildcard fall back rather than throw (see the comment in
   `request.ts` — a throw here once made every page 500).
3. **`cs`** otherwise.

On a first visit the server can only guess and cannot set a cookie mid-render, so
`src/components/locale-bootstrap.tsx` persists the guessed locale as a cookie after mount. The
next request then renders the same language without renegotiating — no flash of the wrong
language, and a guest who later changes their browser language keeps what they saw.

The URL never carries the locale. A share link is printed on cards and forwarded in chats; a
`/fr/` prefix would be one more thing to get cut in half, and the switcher would change an
address that must stay stable (CLAUDE.md, "Renames never change a URL").

## The switcher

`src/components/locale-switcher.tsx` — a segmented pill with one 44 px segment per language,
rendered on the marketing page, the wedding hub and the gallery header. Three segments is the
most this pattern comfortably takes on a phone; a fourth language should turn it into a menu.
Its accessible name lists every language by its own name ("Čeština / English / Français"), so
a screen-reader user who speaks only one of them still recognises theirs. The endonyms are
identical in every catalog for the same reason.

## Writing a catalog

- **Register**: Czech addresses the guest as "ty" (a friend forwarded you this). English is
  neutral. French uses **"vous"** throughout — the norm on French sites even for warm,
  informal brands, and the only safe choice for a link that reaches every generation of a
  wedding. Keep new French strings in "vous".
- **Plurals** are ICU `{count, plural, …}`; each language uses its own CLDR categories (table
  above). French `one` covers 0 as well as 1 ("0 photo"), which ICU handles — do not special-case
  zero.
- **French typography**: a non-breaking space (U+00A0) before `?`, `!`, `:`, `;` and `%`, and
  inside `« »`. `messages/fr.json` already has them; keep them when editing.
- **Placeholders and tags** (`{size}`, `<a>…</a>`) must survive translation.
  `src/i18n/messages.test.ts` fails on a missing key, an extra key, or a lost placeholder in
  any catalog.
- Dates go through `src/lib/format-date.ts`, never `toLocaleDateString` with a literal tag —
  it maps the bare code to the `Intl` tag and pins `Europe/Prague`.

## Adding a language

1. Append the code to `LOCALES`, `LOCALE_TAGS` and `OG_LOCALES` in `src/i18n/locales.ts`.
2. Add `messages/<code>.json` — copy `en.json`, translate every key, keep placeholders.
3. Add the language's own name under `localeSwitcher` in **every** catalog.
4. Add the printable sign's copy in `src/components/printable-sign.tsx` (TypeScript fails until
   you do — the copy tables are `Record<Locale, …>`).
5. Add negotiation cases to `src/i18n/request.test.ts`, a date case to
   `src/lib/format-date.test.ts`, and an autodetection case to `e2e/locale-switch.spec.ts`.
6. Reconsider the switcher (above) at four languages.

`pnpm test` is what tells you the catalog is complete; there is no runtime fallback to English
for a missing key, only next-intl's console error.
